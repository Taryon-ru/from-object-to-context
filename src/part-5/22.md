
### Глава 22. Row-Level Security

#### 22.1. RLS как последняя граница

RLS применяется там, где модель безопасности должна быть непосредственно отражена в ограничении физических строк. Архитектурная цепочка:

```
Security model
      ↓
Effective authorization
      ↓
RLS policy
      ↓
Physical rows
```

RLS находится на уровне физического хранения. Он не должен заново строить всю модель отношений.

---

#### 22.2. Почему RLS не должен вычислять весь граф

Предположим, доступ зависит от:

```
User
 → Group
 → Parent Group
 → Project
 → Role
 → Publication
 → Object
```

Можно попытаться построить весь этот граф внутри каждой RLS policy. Но тогда база данных становится одновременно:

- хранилищем;
- движком отношений;
- движком проекций;
- движком авторизации.
    

Гораздо устойчивее подготовить необходимые security facts заранее:

```
Relationships
      ↓
Security projections
      ↓
RLS
```

База данных применяет подготовленное правило к данным, а не заново строит всю модель отношений.

---

#### 22.3. RLS использует подготовленное состояние

RLS получает информацию, необходимую для физического ограничения запроса. Например:

```
current_company_id
current_user_id
```

и связанные с ними производные данные. В результате:

```
Projection layer
```

подготавливает модель, а:

```
RLS
```

применяет её к данным.

---

#### 22.4. Контекст запроса должен быть доверенным

Если RLS использует:

```
current_user_id
current_company_id
```

возникает вопрос, кто устанавливает эти значения. Они не должны зависеть от произвольного пользовательского SQL. Контекст должен формироваться доверенным приложением или другим контролируемым механизмом. Иначе RLS не сможет быть надёжной границей безопасности.

---

#### 22.5. Транзакция и соединение

Контекст безопасности должен относиться к конкретному SQL-сеансу или транзакции. Иначе connection pool может привести к опасному сценарию:

```
Request A
    ↓
connection
    ↓
security context A

connection returned to pool

Request B
    ↓
same connection
    ↓
old context A
```

Поэтому управление контекстом соединения является частью архитектуры RLS.

---

#### 22.6. Как это реализовано в Guardian

В текущей реализации Guardian используется `RlsDataSourceProxy`. Архитектура разделяет:

```
physicalDataSource
```

и:

```
RLS-aware application DataSource
```

Физический источник используется инфраструктурными операциями, в частности Flyway. Приложение получает прокси над физическим источником. Прокси применяет RLS-контекст перед выполнением бизнес-SQL на том же физическом соединении. Схема выглядит так:

```
Hikari physical connection
        ↓
RlsDataSourceProxy
        ↓
business SQL
        ↓
PostgreSQL RLS
```

---

#### 22.7. Почему RLS применяется перед бизнес-запросом

Соединение может быть получено заранее, когда бизнес-запрос ещё не выполняется. Поэтому применение контекста связывается с началом выполнения бизнес-SQL. `SET LOCAL` выполняется на том же физическом соединении, на котором выполняется запрос. Это связывает security context с конкретной транзакцией.

---

#### 22.8. RLS и миграции

Инфраструктурные операции не должны случайно оказаться внутри обычной пользовательской модели доступа. В Guardian:

```
Flyway
   ↓
physicalDataSource
```

а:

```
Hibernate / repositories
   ↓
RlsDataSourceProxy
```

Это разные пути. Так сохраняется различие между инфраструктурным контекстом и контекстом бизнес-запроса.

---

#### 22.9. Разные операции требуют разных политик

Чтение и изменение данных не обязаны иметь одинаковую политику. Например:

```
SELECT
```

может требовать `READ`.

А:

```
UPDATE
```

может требовать:

```
UPDATE
+
additional state condition
```

Поэтому RLS-политики должны соответствовать конкретным операциям.

---

#### 22.10. RLS не заменяет объектную авторизацию

RLS может ограничивать строки, но это не означает, что он должен отвечать на все вопросы бизнес-авторизации.

Например: Может ли пользователь согласовать объект?

Это может зависеть от роли, состояния, проекта и других отношений.

А вопрос: Какие строки таблицы доступны этому SQL-запросу?

естественно решается на уровне RLS. Разделение ответственности:

```
Authorization model
        ↓
Object authorization
        ↓
Data enforcement
```

---

#### 22.11. Главный вывод

RLS — не модель доступа. Это механизм, который превращает решение модели безопасности в физическое ограничение данных. Полная схема:

```
Source facts
      ↓
Security projections
      ↓
Effective authorization
      ↓
Object authorization
      ↓
RLS
      ↓
Physical rows
```

Чем сложнее отношения в модели, тем важнее не переносить их целиком в RLS. База данных должна применять подготовленное правило к данным.

---
