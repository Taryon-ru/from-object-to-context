
### Глава 17. Проекции безопасности

#### 17.1. Почему появляется проекция

К этому моменту модель содержит несколько уровней:

```
Source facts
    ↓
Relationships
    ↓
Context
    ↓
Rules
    ↓
Effective permissions
```

Если все эти вычисления выполнять непосредственно во время каждого запроса, проверка доступа может превратиться в обход сложного графа отношений. Поэтому часть результата можно вычислить заранее.

Так появляется **проекция безопасности**.

Проекция — это производное представление исходной модели, подготовленное для определённого класса проверок.

---

#### 17.2. Проекция не является источником истины

Проекция не должна становиться независимым источником состояния. Например:

```
UserGroupLink
```

является исходным фактом.

А:

```
effective_user_group
```

является производным представлением. Если удалить исходную связь, проекция должна измениться. Поэтому:

```
Source facts → Projection
```

а не:

```
Source facts ↔ Projection
```

Проекция существует для вычисления и последующей проверки.

---

#### 17.3. Какие результаты имеет смысл материализовать

В сложной системе обычно не требуется заранее создавать запись для каждой комбинации:

```
User × Action × Object
```

Такой объём данных может быть слишком большим. Гораздо полезнее материализовать устойчивые промежуточные результаты. Например:

```
effective_user_group
effective_user_permission
object_scope
```

Они представляют разные части модели.

`effective_user_group` описывает производные отношения субъекта и групп.

`effective_user_permission` содержит эффективные разрешения субъекта в определённых областях.

`object_scope` описывает области и основания доступа, связанные с объектом.

---

#### 17.4. Проекция строится из фактов и правил

Концептуально построение выглядит так:

```
Source facts
     ↓
Security rules
     ↓
Derived security facts
     ↓
Projection
```

Для конкретной проекции этот процесс можно представить следующим образом:

```
function rebuildProjection(sourceFacts):
    relevantFacts = selectRelevantFacts(sourceFacts)
    derivedFacts = deriveSecurityFacts(
        relevantFacts,
        securityRules
    )
    replaceProjection(derivedFacts)
```

Проекция является результатом применения правил к исходным фактам.

---

#### 17.5. Проекции Guardian

В Guardian значительная часть оснований доступа материализуется заранее. Например:

```
KUserGroupLink
      ↓
effective_user_group
      ↓
Scope Barrier
      ↓
effective_user_permission
```

Отдельно:

```
KPublish
      ↓
object_scope
```

Для владельца существует отдельный `OWNER`-scope в `object_scope`. Поэтому при обычной проверке объекта система не должна заново обходить всю модель отношений. Она использует уже подготовленные результаты.

---

#### 17.6. Роль `effective_user_group`

`effective_user_group` участвует в построении производных разрешений и обработке Scope Barrier. Результат этой обработки материализуется в:

```
effective_user_permission
```

Поэтому непосредственная проверка объекта использует:

```
effective_user_permission
object_scope
```

а не заново вычисляет групповую модель. Это разделяет два процесса:

```
построение эффективных разрешений
```

и:

```
проверка конкретного запроса
```

---

#### 17.7. Проекция не является окончательным решением

Наличие записи в проекции само по себе не означает:

```
ALLOW
```

Например:

```
effective_user_permission = READ
object_scope = UPDATE
required = UPDATE
```

не даёт разрешения. Проекция предоставляет данные, необходимые для применения правила. Поэтому следует различать:

```
Projection
```

и:

```
Authorization decision
```

---

#### 17.8. Проекция — часть архитектуры вычисления доступа

Без проекций:

```
Request
   ↓
Graph traversal
   ↓
Rules
   ↓
Decision
```

С проекциями:

```
Source changes
      ↓
Projection building
      ↓
Prepared security facts

Request
      ↓
Prepared security facts
      ↓
Decision
```

Стоимость сложной модели переносится с каждого запроса на обработку изменений исходных фактов. Это не устраняет вычисления, но позволяет выполнять их один раз и использовать результат многократно.

---

#### 17.9. Главный вывод

Проекция безопасности должна отвечать на конкретный класс вопросов.

Она:

- имеет понятный источник;
- строится по определённым правилам;
- имеет понятную область применения;
- может быть пересоздана;
- не является самостоятельным источником истины.
    

Поэтому безопасность можно рассматривать как отдельный производный слой над моделью предметной области:

```
Domain facts
      ↓
Security-relevant facts
      ↓
Security projections
      ↓
Authorization
```

Следующий вопрос связан с изменением исходных данных: если один факт используется несколькими производными представлениями, изменение этого факта должно распространиться по всей зависимой части модели.
